## Задача

Реализовать `HttpRequestParser` как оболочку, которая получает произвольную последовательность физических фрагментов сокета и собирает из них ровно один логический HTTP-запрос. Оболочка управляет автоматом заголовков, будущим автоматом тела и возвращает таблицу offsets вместе с ареной без материализации `String`, `Map` и объектов заголовков.

## Архитектурный контракт

- `HttpRequestParser` владеет одним экземпляром `WirthHttpParser`.
- `WirthHttpParser` хранит живое состояние внутри экземпляра; `parse(byte[])` не создаёт объект состояния на каждый фрагмент.
- Границы физических чтений семантически невидимы.
- Все offsets задают полуоткрытые интервалы `[startInclusive, endExclusive)`.
- Конец заголовков фиксируется сразу после последнего `LF`; байты тела и следующего запроса не поглощаются первым автоматом.
- Готовый результат содержит offsets и арену; материализацию выполняет потребитель.
- Один экземпляр оболочки обслуживает один логический запрос. Правила повторного использования и передачи владения ареной фиксируются отдельно.

## Текущая контрольная точка

- [x] Состояние перенесено из создаваемого на каждом чанке `WirthParsedData` внутрь `WirthHttpParser`.
- [x] `WirthHttpParser.parse(byte[])` возвращает только `STATUS`.
- [x] Для `standardGet` цельный и побайтовый проходы дают одинаковые статус, `consumedBytes`, `nextOffsetIdx` и offsets при независимых таблицах.
- [x] `HttpRequestParser` возвращает `ParserState`, а серверный стенд принимает этот статус.
- [x] Обычный цельный запрос прошёл живой тракт под `wrk`.

## Следующие проверки

- [ ] Явно проверить ожидаемые `FINISHED` и `consumedBytes == payload.length` в стенде Вирта.
- [ ] Проверить цельную и побайтовую подачу через два независимых экземпляра `HttpRequestParser`.
- [ ] Проверить разрезы внутри URI, имени и значения заголовка, между `CR` и `LF`.
- [ ] Возвращать `NEEDS_MORE_DATA`, `FINISH` и `ERROR` без смешения исходов.
- [ ] Создавать итоговый `ParsedData` только при завершении логического запроса.
- [ ] Подключить арену и определить её фактическую заполненную длину.
- [ ] Сохранить точную границу заголовков при наличии тела в том же фрагменте.
- [ ] Сохранить остаток, относящийся к следующему запросу.
- [ ] Продолжать чтение сокета после `NEEDS_MORE_DATA`.

## Известные огрехи текущего WIP

- `ERROR` в `HttpRequestParser` сейчас попадает в ветку `FINISH`.
- В оболочке остались неиспользуемые поля и экземпляр старого `WirthParsedData`.
- Сам record `WirthParsedData` и старые импорты ещё не удалены.
- Собственные offsets оболочки не связаны с таблицей, которой владеет Вирт.
- Ручной стенд оболочки печатает трассу, но пока не содержит assertions.
- Вирт после перехода в `FINISHED` продолжает обход остатка текущего массива и увеличивает `consumedBytes`.
- Серверный стенд выходит из цикла чтения после `NEEDS_MORE_DATA`.

## Производительность

Цель горячего пути — отсутствие новых объектов состояния на физический фрагмент. Один итоговый снимок на завершённый логический запрос допустим до появления измерений, доказывающих обратное. Результаты нагрузочных прогонов ведутся в `doc/benchmarks/http-server.md`.
